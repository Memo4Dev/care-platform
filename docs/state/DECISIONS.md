- M1-004: A branch-scoped role grant always implies branch access. `User.assignRole` writes the corresponding `branch_access` row on first grant; explicit `branch_access` also supports view-only access with no role. Revoking a role retains access, and revoking access is rejected until roles at that branch are revoked, so a role can never be stranded outside scope.
- M1-004: Tenant system role templates are editable. `is_system` identifies seeded Owner/Manager/Sales/Cashier/Warehouse/Purchasing/Delivery templates but does not freeze their permission sets; configurable matrix cells are initially denied and can be granted later. No role deletion command exists in this slice.
- M1-004 review remediation: ADR-0002 accepts organization-scoped identity administration, explicit actor enforcement (including public user creation/identity linking), self-escalation denial, and ID-first identity integration events. Bootstrap is only through the dedicated `IDENTITY_PROVISIONING` token with SYSTEM actor.
- M1-004 final remediation: every normal Identity mutation requires a non-SYSTEM human actor, correlation ID, and causation ID; those values are persisted in every outbox envelope. Suspended actors are denied before capability evaluation. The sole SYSTEM exception is atomic idempotent `provisionInitialOwner` on the dedicated provisioning-only provider behind `IDENTITY_PROVISIONING` (not general IdentityService): it resolves only the specified initial identity, creates/validates only fixed approved templates, and grants the seeded Owner role to that identity, emitting architecture-58 version-1 ID-only envelopes. A different established Owner is rejected and no arbitrary-owner grant API exists.
- M1-004 concurrent initial Owner remediation: `identity.initial_owner_assignments` uses `organization_id` as its primary key and composite tenant FKs to record the immutable provisioning claim. `provisionInitialOwner` claims it with INSERT ON CONFLICT semantics in the transaction containing the Owner role grant; a same-user retry is idempotent and a different user receives VALIDATION_FAILED. This preserves unrestricted normal organization-role grants.
- M1-004 ownership clarification: `initial_owner_assignments` records only the singleton bootstrap initial Owner claim. After bootstrap, an active actor with organization-scoped `role-grants.manage` may grant the Owner template (or any organization role) to another user; self-grants remain denied. Owner is therefore not permanent singleton authority.
- M1-004 final remediation: the durable bootstrap claim alone determines `provisionInitialOwner` retry idempotency, so later authorized Owner grants or revocations never create a new claim or bootstrap grant. Every identity-administration transaction acquires the same transaction-scoped PostgreSQL advisory lock for its organization before evaluating authorization; role, permission, and organization-role grant mutations use that lock too, preventing authorization TOCTOU within the context.
- M1-005: Plans are global versioned aggregates; tenant overrides are separately scoped aggregates and may only be granted by an Identity user belonging to the same organization, enforced by a composite FK. Entitlement evaluation requires an active Subscription supplied through a context contract and an ACTIVE plan; business consumers receive only capability-code answers and never plan metadata. M1-006 owns the production SubscriptionStatus adapter.
- ADR-0003 accepted: Architecture-58 uses one scope-validated envelope. `TENANT` requires a non-null `organizationId`; `GLOBAL` requires `organizationId: null`. Plan events are GLOBAL; tenant overrides and other tenant-context events are TENANT. Consumers validate both fields instead of assuming every event has a tenant.
- M1-005 security remediation: Generic outbox envelopes are ID-first minimized contracts. Producers may emit only identifiers, capability/business codes, lifecycle status, priority and event metadata required for integration; display names and policy values remain in the owning bounded context.
- M1-006: `SubscriptionStatus` is a read-only module contract implemented by Subscription & Billing and consumed by Entitlements; it exposes only organization ID, plan ID, and business-access status. TRIAL and ACTIVE permit entitlement resolution; PAST_DUE, SUSPENDED, CANCELLED, and EXPIRED fail closed. Subscription lifecycle outbox events are architecture-58 TENANT envelopes, and a PostgreSQL partial unique index is the concurrency authority for one non-terminal commercial subscription per organization.
- M1-006 blocker remediation: even TRIAL and ACTIVE states grant business access only while their respective `trial_ends_at` and `current_period_end` instants are strictly in the future. Subscription-period history is physically immutable in PostgreSQL: an additive trigger rejects UPDATE/DELETE with SQLSTATE `55000`, while new history remains INSERT-only.
- M1-007: Platform Management owns only operator metadata in `platform.tenants`; it references but does not mutate Organization business history or Subscription state. Platform Tenant lifecycle is `REGISTERED → ACTIVE ↔ SUSPENDED → CLOSED`, activation/reactivation require completed provisioning, and suspension requires a reason. Platform roles are a static policy separate from tenant RBAC: Platform Owner performs lifecycle commands, Platform Support manages support sessions, and Billing Admin cannot suspend tenants.
- M1-007: Support sessions are explicit operator records, never tenant-user impersonation: required reason, requester/starter/ender IDs and timestamps, required future expiry, visible session identity, end reason/status, and time-bound active evaluation. Session and tenant lifecycle events use architecture-58 TENANT envelopes because they are scoped to the target Organization.
- ADR-0004 accepted by human decision: Platform authorization is database-backed and independent of tenant RBAC. Authenticated Supabase identities map to active platform principals; server-side role/capability assignments determine permission, never caller-supplied role values. Support session use is bound to the requesting platform principal and expiry commits its audit/outbox effect before denial.
- ADR-0005 accepted: trusted authenticated-principal contexts are the only identity proof accepted by application services; platform users resolve from verified Supabase subjects and SYSTEM_SERVICE is server-factory-only.
- M1-007 test remediation: Nest application services explicitly inject class-based repository tokens where reflected metadata can be erased by the Vitest transform. This preserves the existing provider contract and avoids bootstrap worker termination; Vitest pool/concurrency configuration is unchanged.
- M1-008: Tenant Provisioning owns resumable process state only. The Platform Tenant/Organization/Identity/Subscription remain in their owning contexts; the process manager calls narrow contracts and uses deterministic default branch/warehouse/owner IDs so retried deliveries cannot duplicate defaults. Storefront remains deliberately unimplemented in M1: entitlement is resolved and its skipped checkpoint is recorded; Platform completion is invoked only after all mandatory checkpoints.
- ADR-0007 accepted by human decision: trusted Platform registration snapshots, not caller input, are the authority for Tenant Provisioning; a tenant-scoped opaque execution capability replaces generic SYSTEM authority and terminal provisioning is serialized/immutable.
- ADR-0008 accepted by human decision: tenant entitlement override attribution uses `actor_type`, `actor_id` and correlation ID. Only active persisted Platform principals or opaque server `SYSTEM:*` actors are valid; organization users are forbidden override grantors.
- M1-009: API bearer JWTs require signature, expiry and configured audience validation before any database principal lookup. Platform and tenant audiences are distinct environment configuration; roles, platform principal IDs, organization IDs and branch scope never come from request bodies.
- M1-009 remediation: API-reachable Nest application services use explicit class repository injection tokens. Reflected constructor metadata is not a reliable dependency contract under the Vitest transform; explicit tokens preserve the existing module providers without relaxing authorization or test coverage.
- M1-009 durability remediation: HTTP idempotency outcomes and integration delivery Inbox records are distinct controls. Retry acceptance commits its workflow reference, HTTP outcome and Outbox event atomically; the consumer uses the outbox EventId only for Inbox deduplication and relies on M1-008 checkpoints for retry-safe recovery.
- M1-009 tenant HTTP remediation: API-reachable identity contract providers use explicit class injection tokens where Vitest transform erases reflected constructor metadata; this preserves the existing authorization contract and does not alter authorization rules.
- M1-009 Platform Admin idempotency: Platform Admin mutations use a local application adapter, not a split HTTP interceptor. The adapter inserts the authenticated route/key request-hash claim, executes the owning context command through the same transaction, persists its Outbox effects and serializes the completed outcome before commit; matching retries replay, different requests conflict, and incomplete claims fail closed.
- M1-009 delivery: approved Outbox→BullMQ is at-least-once delivery with durable PostgreSQL authority. Relay publication uses a row lease and EventId BullMQ job ID; consumer deduplication is per `(eventId, consumer)` Inbox lease, not a global queue acknowledgement. Provisioning retry execution remains checkpoint-resumable, so a crash after command completion and before Inbox completion safely replays the existing process state.
- M1-009 relay review remediation: production relay and worker runtimes require Redis ACL `REDIS_USERNAME` and `REDIS_PASSWORD`; omission is allowed only when both `NODE_ENV=test` and `REDIS_TEST_ALLOW_UNAUTHENTICATED=true` are explicitly set. Every Outbox acknowledgement and Inbox completion/release also predicates on lease expiry, so stale owners cannot mutate a renewed lease. API `/metrics` serves the dedicated Prometheus registry; database-backed backlog/provisioning gauges are refreshed on scrape and BullMQ failed-job gauge is refreshed by relay polling.
- M1-009 final delivery hardening: `/metrics` is an infrastructure-principal endpoint, not a public health endpoint. It requires exact bearer authentication against the deployment-provided `METRICS_BEARER_TOKEN`; missing configuration and invalid/missing credentials return the same authentication failure before querying PostgreSQL. Network policy must independently restrict the endpoint to Prometheus. CI disables Redis `default` only after provisioning and validating the scoped authenticated `ci` ACL user, and all CI BullMQ operations use that user.
- M1-009 tenant bearer hardening: an active Identity user is insufficient to establish tenant authority. `TenantBearerGuard` must resolve a linked Platform Tenant and requires `status = ACTIVE` plus `provisioningStatus = COMPLETED` before constructing the trusted organization principal. Missing/incomplete provisioning uses the catalogued `TENANT_PROVISIONING_INCOMPLETE` error; unavailable tenant lifecycle states (`SUSPENDED` and `CLOSED`) use the catalogued `TENANT_SUSPENDED` error rather than introducing a breaking error code.
- M1-010 validation record: the M1 exit flow requires the bootstrap Owner to hold explicit access to the deterministic default branch. Tenant Provisioning requests that access only through the narrow `IDENTITY_PROVISIONING` contract after Organization creates the default branch; it does not write Identity persistence directly. Local native PostgreSQL success remains insufficient for Outbox/BullMQ delivery: authenticated Redis CI coverage with `REDIS_INTEGRATION=true` is a mandatory pre-acceptance gate after push.
- M1-010 concurrency hardening: tenant branch/warehouse mutation transactions acquire a deterministic organization advisory lock before usage/entitlement evaluation and aggregate mutation. This makes distinct-idempotency-key resource-limit races evaluate serially, returning `PLAN_LIMIT_REACHED` to the excess request instead of relying on a stale aggregate CAS conflict.

- M2-010 Idempotency: `platform.claims` uses INSERT ON CONFLICT with `(key, request_hash)` for atomic claim acquisition; `platform.idempotency_outcomes` stores the full HTTP response for durable replay; both tables reference `platform.tenants` with composite FKs. Claims and outcomes are always in the same transaction as the business mutation and Outbox events. This is a local idempotency pattern (not global distributed), scoped to the API layer; the same pattern from M1-009 Platform Admin idempotency is extended to Catalog and Pricing mutations.
- M2-011 HTTP boundary tests: Catalog controller requires `catalog.read`/`catalog.write` permission codes which are NOT in the `PERMISSION_CODES` array — tests document intended behavior (403 PERMISSION_DENIED) and will need updating when permission codes are added. Pricing controller only requires principal type ORGANIZATION_USER (no specific permission codes), so successful CRUD works through HTTP once tenant is provisioned. Tests follow the exact api.integration.spec.ts pattern for consistency.
- M2-012 Integration tests: direct persistence tests follow the organization.integration.spec.ts pattern with `createTestDatabase()`, vitest `describe`/`it` blocks, and real PG assertions. All money values are numeric strings per ADR-0002 boundary contract; field names are verified via raw SELECT to catch Drizzle schema drift; two-decimal-place precision is enforced in the database layer (NUMERIC(12,2)). Unique constraint violations map to 23505 PostgreSQL error codes which the repository layer translates to VALIDATION_FAILED.
- M2-013 Cross-tenant isolation: all cross-tenant tests create a complete independent organization with branch, owner user with branch access, subscription (ACTIVE, MONTHLY), and platform tenant (ACTIVE, COMPLETED) to ensure isolation is enforced at the query level (organization-scoped Drizzle queries), not just at the HTTP guard level. Foreign-tenant negative reads prove data is never leaked across organization boundaries in any domain table.
- M2-CATALOG-001: `catalog.read` and `catalog.write` are not in `PERMISSION_CODES` — the authorization evaluator rejects them as PERMISSION_UNKNOWN → PERMISSION_DENIED. This is a known gap: the permission codes must be added to the `PERMISSION_CODES` array and seeded into the database before catalog CRUD endpoints work through HTTP. The catalog HTTP tests document this expected behavior.
- POS AUTH-001: POS quick operator authentication requires Employee Card/Barcode + PIN; barcode/card alone is never sufficient. Employee barcode/card must use an opaque credential identifier (no email, role, organizationId, or permissions encoded). Operator authentication is separate from authorization: after successful Card + PIN, resolve server-side RBAC, branch scope, and POS permissions.
- CASH SESSION-001: A Cash Session is exclusively bound to one POS Device, one Cash Drawer, one Employee, and one active shift/session. Multiple employees must not hold simultaneous active Cash Sessions on the same drawer. Shift handoff requires closing the existing Cash Session before another operator opens a new one on that drawer.
- CASH SESSION-002: Cash count and reconciliation on Cash Session close is enabled by default (`cashSession.requireReconciliationOnClose = true`). Organization policy may disable mandatory reconciliation, but session close remains fully audited regardless.
- CASH SESSION-003: Manager approval at POS may use Manager Card + PIN without replacing or logging out the active cashier. Record `performedBy = active cashier` and `approvedBy = manager` for audit.
- POS OFFLINE-001: POS operator authentication and Cash Session operations must remain compatible with offline POS operation. Operator identity is verified against locally cached credentials; authorization uses last synced permission snapshot; session operations queue locally and reconcile on sync.
- M3-001: Inventory is tracked per Organization + Branch + Warehouse + Variant. The core balance formula is `Available = OnHand - Reserved - Allocated`. There are no direct quantity edits; corrections happen through Adjustment transactions. FIFO is the costing strategy (oldest remaining cost layers first). The ledger is append-only and immutable.
- M3-001: `inventory.stock_positions` has a composite UNIQUE constraint on `(organization_id, warehouse_id, variant_id)` and CHECK constraints ensuring `reserved + allocated <= on_hand` and all quantities non-negative. The warehouse table gained a `warehouses_tenant_scope_unique` composite UNIQUE on `(id, organization_id)` to support inventory FK references.
- M3-001: `inventory.fifo_layers` are append-only with a partial index on `remaining_quantity > 0` to accelerate oldest-first consumption queries. `inventory.ledger_entries` uses DB-side `gen_random_uuid()` for IDs and is immutable.
- M3-004: `inventory.create` permission code is seeded via migration `0025_add_inventory_permissions.sql`. Combined with pre-existing `inventory.view`, `inventory.adjust`, and `inventory.transfer` from M1 migration `0002_dark_shard.sql`. OWNER and ADMIN get full inventory permissions; SALES and WAREHOUSE get read-only (`inventory.view`).
- M3-005: Inventory HTTP controller uses 21 endpoints with Zod validation, Swagger decorators, idempotency enforcement, and authorization checks via `IDENTITY_CONTRACTS.authorize()`. Registered in `api.module.ts` with Swagger tag "Inventory".
- M3-006-009: Domain tests (136 unit) run without database; integration/concurrency/HTTP-boundary tests require `TEST_DATABASE_URL`. Domain tests use pure aggregate manipulation with mock clocks. Integration tests use real PostgreSQL via `createTestDatabase()`.
- M3 concurrency: `InventoryRepository` uses `SELECT ... FOR UPDATE` on stock position and FIFO layers for pessimistic locking. Idempotency claims and outcomes are in the same transaction as business mutations.
